# System design

**Status:** design draft; a D0 subset is implemented, with no full-system assurance claim
**Last updated:** 2026-08-01
**Owner:** to assign

## 1. Design objective

LAIcode should let a developer define a bounded region of a program that may
evolve, then run an external control loop that proposes, evaluates, and promotes
candidate versions using declared evidence.

The design prioritizes six properties:

1. **Judge–candidate separation:** mutable code cannot modify or impersonate the
   mechanism that scores it.
2. **Constraint precedence:** safety and correctness constraints are gates, not
   terms that can be traded away in a weighted score.
3. **Replayable decisions:** an independent operator can reconstruct why every
   candidate was accepted or rejected.
4. **Bounded authority:** permissions, mutation surface, resource use, and rollout
   are denied unless declared.
5. **Empirical humility:** a successful evaluation is evidence scoped to an epoch
   and workload, not a universal claim of superiority.
6. **Semantic learner interface:** machine learners manipulate canonical typed
   program objects and receive structured, provenance-bearing feedback rather
   than relying only on whole-file source generation and compiler prose.

## 2. System boundary

```text
                       TRUSTED GOVERNANCE / CONTROL PLANE
  ┌────────────────────────────────────────────────────────────────────┐
  │ Contract + policy compiler       Capability / lease / key service │
  │ Evidence partition manager       Verifier + promotion controller  │
  │ Artifact registry + deployer     Recovery controller + ledger     │
  └───────────────┬──────────────────────────────┬─────────────────────┘
                  │ permitted evidence           │ exact-artifact leases
                  ▼                              ▼
  ┌──────────────────────────┐     ┌───────────────────────────────────┐
  │ UNTRUSTED SEARCH PLANE   │     │ ISOLATED APPLICATION PROCESSES   │
  │ selectors / optimizers   │     │ champion / shadow twin / canary  │
  │ typed actions / learners │     │ candidate diagnostics are tainted│
  └─────────────┬────────────┘     └────────────────┬──────────────────┘
                │ candidates                        │ candidate outputs
                ▼                                   ▼
  ┌──────────────────────────┐     ┌───────────────────────────────────┐
  │ ISOLATED CANDIDATE LAB   │     │ TRUSTED EXECUTION GUARD          │
  │ build / replay / attack  │     │ reference monitor / output shield│
  └──────────────────────────┘     │ independent metrics / router      │
                                   └────────────────┬──────────────────┘
                                                    │ authenticated data
                                                    ▼
                                   ┌───────────────────────────────────┐
                                   │ EVIDENCE + PROVENANCE STORAGE     │
                                   │ append-only hashes/decisions      │
                                   │ separately deletable raw payloads │
                                   └───────────────────────────────────┘
```

The control plane is stable within an evolution epoch. The search plane and
application candidates are treated as untrusted even when they were generated by
project-owned code.

The initial prototype may run components on one machine, but untrusted search or
candidate code never shares the control plane’s process, operating identity,
credentials, or address space. Candidate diagnostics are tainted inputs; only
independent or externally attested collectors supply promotion/rollback metrics.

## 3. Trusted computing base

The trusted computing base (TCB) is deliberately small in authority, though not
necessarily small in code size.

### 3.1 Contract compiler

Parses the evolution contract, rejects ambiguous or unsupported policies, and
produces a normalized, content-addressed epoch policy. It performs no candidate
generation.

### 3.2 Capability broker

Issues short-lived, least-privilege capabilities to build, evaluation, shadow,
and canary jobs. Candidates receive no ambient credentials and cannot mint
capabilities.

### 3.3 Evidence partition manager

Controls access to search, operational-holdout, research-audit, and prospective
evidence.
Candidate generators may consume only partitions declared for search. The
manager records every disclosure because repeated test access changes the
statistical meaning of a result.

### 3.4 Verifier registry

Runs versioned correctness, safety, compatibility, and resource checks. A
candidate may provide additional evidence, but cannot replace a required
verifier or turn a failed required check into a pass.

### 3.5 Promotion controller

Evaluates transition guards, grants deployment leases, controls traffic
allocation, and records the complete decision. It never executes candidate code
with its own privileges.

### 3.6 Rollback controller

Maintains at least one known-recoverable champion, watches independent health
signals, revokes a candidate lease, and restores the prior version. Candidate
telemetry alone cannot suppress rollback.

### 3.7 Candidate ledger

Stores the append-only version graph and evidence manifest. Corrections append a
new record; they do not rewrite history.

### 3.8 Execution guard and trusted metric collectors

Mediates candidate outputs before they affect the managed system, applies
runtime-enforceable constraints, substitutes a reviewed fallback when policy
allows, and independently records outcomes and resource use. Candidate-provided
diagnostics are never the only source for a promotion or recovery decision.

### 3.9 Artifact registry, deployer, and traffic router

Stores exact immutable artifacts, verifies content identities when leases are
issued, starts isolated processes, and routes shadow/canary/champion traffic. The
deployer runs only artifacts authorized by a signed controller event.

### 3.10 Signing, trusted time, and lease service

Protects governance keys, signs epoch and deployment decisions, supplies the
trusted time used for expiry and cooldown semantics, and ensures candidates
cannot extend their own resource or deployment leases.

### 3.11 Evidence storage

Stores authenticated metrics and provenance. Hashes, schemas, decisions, and
deletion tombstones are append-only. Sensitive raw payloads live in separately
encrypted storage with retention expiry or cryptographic erasure so auditability
does not defeat privacy deletion requirements.

### 3.12 Lower-level assurance dependencies

The host kernel/hypervisor, sandbox runtime, compiler or interpreter used for
confinement, cryptographic implementation, and storage platform are not all
control-plane services, but they are explicit assurance dependencies. Their
versions and residual risks are recorded for every claim.

### 3.13 Candidate semantic kernel and action validator

Defines the canonical candidate IR, types, effects, holes, permitted construction
actions, lowering rules, and machine-readable diagnostics. It validates every
accepted model action and content identity. Because the model-facing interface
depends on its semantics, the kernel is trusted and versioned per epoch; the
learner, learned libraries, candidate construction sessions, and free-form model
output remain untrusted.

## 4. Evolution contract

The contract is the governance-facing language contribution. A distinct
model-facing candidate IR and semantic action protocol are defined below and in
the model-native programming design. The following contract syntax is a strawman
designed to expose semantics, not a commitment to surface grammar:

```text
evolution cache_policy @ epoch "2026-01" {
  target {
    entry       = cache::select_victim
    observation = CacheAccessObservationV1
    precondition snapshot.evictable_keys is_not_empty
    fallback    = reviewed::lru_select_victim
  }

  mutable {
    region "eviction_policy"
    ast    CachePolicyIRv1
    state  none
    deny   [io, network, clock, randomness, unsafe]
  }

  require {
    prove effects(candidate) subset_of [read_snapshot]
    runtime_enforce result in snapshot.evictable_keys fallback=target.fallback
    runtime_enforce result not in snapshot.pinned_keys fallback=target.fallback
    runtime_enforce peak_memory <= 256 MiB action=terminate_candidate
    test candidate_violation_rate == 0 on operational_holdout
    statistically_monitor crash_rate <= 1e-4 confidence=0.99 min_events=100_000
  }

  optimize constrained {
    primary minimize miss_ratio practical_delta=0.02
    protect p99(decision_latency) noninferior_tolerance=0.05
    secondary minimize p99(decision_latency)
  }

  evidence {
    search              = window("train", last=14d)
    operational_holdout = window("selection", next=2d)
    research_audit      = dataset("audit-v1") use=post_decision_freeze
    prospective         = counterfactual_shadow(min_events=100_000, min_duration=24h)
  }

  accept {
    method paired_anytime_valid
    epoch_false_promotion_budget <= 0.05
    max_candidate_comparisons <= 100
    target_power >= 0.80 for practical_delta(miss_ratio)=0.02
  }

  budget per_epoch {
    candidates <= 100
    cpu <= 24 core_hour
    wall <= 6 hour
    money <= 20 USD
  }

  rollout {
    counterfactual_shadow 100% for 24h
    canary [1%, 5%, 25%] hold_each=2h
    shield candidate_output with target.fallback
    recover_on constraint_failure
    rollback_on p99(latency) regression > 0.10 for 5m
  }
}
```

### 4.1 Contract semantic categories

The language must distinguish categories that ordinary configuration formats
often blur:

| Category | Meaning | Can candidate trade it off? |
| --- | --- | --- |
| `require prove` | property discharged by a trusted checker under stated semantics | No |
| `require runtime_enforce` | reference monitor prevents or substitutes a forbidden effect | No |
| `require test` | finite predeployment evidence; never an `always` guarantee | No |
| `require statistically_monitor` | probabilistic evidence/trigger with declared uncertainty | No |
| `optimize` | objective dimension | Only under declared dominance rule |
| `accept` | evidence threshold for promotion | No |
| `budget` | search and operation resource ceiling | No |
| `mutable` | syntactic and capability change boundary | No |
| `evidence` | permitted data flow and disclosure | No |
| `rollout` | deployment state machine and stop rules | No |

### 4.2 Hard constraints before objectives

Candidate comparison is lexicographic:

1. reject any candidate that fails a hard constraint;
2. reject candidates without sufficient required evidence;
3. apply non-inferiority rules on protected dimensions;
4. compare remaining objective vectors;
5. prefer the simpler or lower-risk candidate when results are practically tied.

A weighted sum must not allow a latency improvement to compensate for a failed
required gate. A `test` or `statistically_monitor` requirement can still fail in
an unobserved execution; it is a hard decision rule, not a prevention guarantee.

Only a property discharged by the declared `prove` semantics or prevented by a
trusted `runtime_enforce` mechanism may be described as holding “always” within
that model. A runtime monitor followed by recovery detects a violation; it does
not retroactively prevent it.

### 4.3 Multi-objective semantics

The language supports constrained, lexicographic, and Pareto comparison with
confidence bounds and practical effect sizes. Scalar utility is permitted only
when:

- units and normalization are explicit;
- weights and sensitivity analysis are recorded;
- hard constraints remain outside the scalar score;
- the choice is frozen for the epoch.

### 4.4 Mutation scope

Mutation scope has three layers:

1. **syntactic:** files, declarations, typed AST nodes, or parameters that may
   differ;
2. **semantic:** APIs, invariants, and observable behaviors that must remain;
3. **capability:** resources and effects the candidate may exercise.

Passing a source diff check is not enough. Generated build scripts, dependencies,
dynamic loading, and indirect effects are part of the mutation surface.

### 4.5 Temporal semantics

Some requirements concern traces rather than single calls, for example “each
accepted payment has exactly one ledger record.” The contract should eventually
support monitorable temporal properties. The first prototype restricts itself to
pure targets and finite replay assertions so that semantics are unambiguous.

### 4.6 Two authoritative language layers

The system must not conflate the language that authorizes change with the
language in which a learner constructs a solution:

| Layer | Defines | Authority |
| --- | --- | --- |
| evolution contract | objectives, constraints, evidence, budgets, mutation and rollout | human governance; candidate-immutable within epoch |
| candidate semantic IR | typed executable terms, effects, holes, actions, and transparent abstractions | learner may construct only within contract scope |

A human-readable source form is a projection of the canonical candidate IR. Text
formatting and generated identifiers do not determine candidate identity.

The candidate IR uses a stable semantic kernel plus an optional transparent
abstraction layer. Its contents may be fixed, human-provided, run-scoped, or
persistently learned as declared by `L`; interface support at R4 does not itself
prove learning. Every proposed abstraction must lower to the existing kernel and
carry its declared type, effects, dependencies, provenance, and evidence.
Changing primitive semantics, compiler, kernel, or required verifier is a
governance change and starts a new epoch.

### 4.7 Model-facing construction semantics

Candidate construction is an episodic typed transition system rather than only a
one-shot text response. Each action either:

- produces a new canonical `ProgramState` with explicit holes and obligations;
- returns a structured rejection without changing the prior state; or
- requests a capability-controlled probe against permitted search evidence.

The action schema includes operations such as filling a typed hole, introducing
a binding, composing checked terms, applying a registered rewrite, defining or
instantiating a transparent abstraction, requesting an obligation check, and
committing an immutable artifact. Type/effect deltas, counterexamples, traces,
resource vectors, uncertainty, and provenance use versioned schemas.

No construction action can grant evidence access, broaden mutation/effect scope,
authorize deployment, or modify the kernel. The post-freeze research audit is
never available through this protocol.

## 5. Candidate lifecycle

```text
PROPOSED
   │ manifest valid, mutation in scope
   ▼
BUILT ───────────────► REJECTED
   │ static gates           ▲
   ▼                        │ any mandatory failure
VERIFIED                    │
   │ operational evidence   │
   ▼                        │
OPERATIONALLY_EVALUATED ────┘
   │ promotion predicate
   ▼
ELIGIBLE
   │ counterfactual shadow lease
   ▼
SHADOWED ── regression ───► QUARANTINED
   │ canary lease                 ▲
   ▼                              │
CANARY ───────────────────────────┘
   │ all holds pass
   ▼
PROMOTED / PROBATION ── health trigger ──► ROLLED_BACK
   │ sustained horizon                         │
   ▼                                           └─ hard/security fault → QUARANTINED
STABLE_CHAMPION ── superseded ────────────────► RETIRED
```

Every transition is monotonic in the ledger. A rolled-back candidate does not
become “unpromoted”; it gains a rollback event and may not re-enter evaluation
without a new candidate identity. Normal lease expiry stops an execution instance
and records a `lease_expired` event; it is not a regression rollback and does not
erase the candidate’s achieved maturity. A new lease always requires a fresh
signed authorization.

### 5.1 Transition guards

| Transition | Minimum guard |
| --- | --- |
| proposed → built | complete manifest, known parent, scope-valid patch, budget lease |
| built → verified | reproducible build, static policy pass, dependency policy pass |
| verified → operationally evaluated | correctness/property/differential checks pass |
| operationally evaluated → eligible | operational holdout, epoch-risk, and objective rules pass |
| eligible → shadowed | shadow environment capacity and data approval |
| shadowed → canary | prospective correctness and health gate pass |
| canary → promoted/probation | every rollout stage and hold period pass |
| probation → stable champion | sustained horizon and registered evidence pass |
| stable champion → retired | a successor becomes stable or governance retires it |
| deployed state → rolled back | independent regression/recovery trigger |
| any state → quarantined | containment, hard-policy, artifact, or evidence-integrity fault |

## 6. Candidate manifest

Every proposal must produce a machine-readable manifest containing at least:

```text
candidate_id            hash of canonical immutable candidate manifest
artifact_id             digest of exact deployable bytes
epoch_id                normalized contract hash
parent_ids              zero or more candidate IDs
source_artifact         immutable source/package reference
source_diff             normalized semantic and textual diff
generator               name, version, configuration, seed
generation_inputs       disclosed evidence and prompt/input hashes
representation_id       R level, kernel/IR and canonicalization version
action_schema            model action/observation protocol version
feedback_treatment       disclosed diagnostic/execution-feedback schema and level
learner_update_mode      L level and persistent-state policy
learner_update_mechanisms explicit run-search/retrieval/library/weight mechanisms
learner_artifacts        checkpoint, retrieval/library/search-state identities
construction_trace      canonical accepted/rejected action and probe log
actual_system_profile    R/M/G/L/D actually exercised plus F treatment
authorized_ceiling       maximum M/D capabilities granted for the run
mutation_scope_report   requested and actual changed regions
build_environment       toolchain, dependencies, image hash
capability_request      build/evaluation/runtime effects
```

The canonical candidate hash covers `artifact_id`, `epoch_id`, parents, generator
specification, generation-input hashes, representation/action versions, learner
artifact identities and mechanisms, feedback treatment, construction-trace hash,
actual profile/authorized ceiling, mutation report, source diff, build
environment, and capability request. It excludes `candidate_id` itself,
timestamps, evaluations, and mutable controller metadata. A schema version fixes
field ordering and encoding.

Trusted timestamps, submission identity, evaluations, leases, and transitions
are separately signed ledger events that reference `candidate_id` and
`artifact_id`. The candidate is not rebuilt in place between evaluation stages;
promoted bytes must correspond to evaluated bytes.

## 7. Observation and learning pipeline

### 7.1 Observation schema

Each observation should separate:

- request or workload features allowed for learning;
- environment features such as hardware class and load;
- program version and configuration;
- functional outcome and its provenance;
- delayed ground truth, if any;
- latency, memory, energy, tokens, and monetary cost where applicable;
- sampling decision and inclusion probability;
- privacy classification and retention deadline.

Versioned schemas prevent a candidate from silently changing what a metric means.

### 7.2 Data flow

```text
raw execution
    ↓ independent collection / schema validation / privacy filtering
observation catalog + retention-controlled payload vault
    ├── search window ─────────────► candidate generator
    ├── operational holdout ───────► promotion evaluator
    ├── research audit ────────────► one-shot post-decision study evaluation
    └── future window ─────────────► prospective generalization report
```

The candidate sees only the search window unless the contract explicitly grants
more. Evaluation outputs should expose the least feedback needed for search;
fine-grained hidden-test feedback can leak the test set over generations. The
research audit is run only after the current study’s search and operational
decisions are frozen. If its result changes later search or design decisions, it
is retired from audit use and becomes disclosed historical evidence.

### 7.3 Separate application adaptation from learner learning

Version selection, parameter tuning, rewrite discovery, and candidate promotion
can adapt the application without changing the generator. Learner learning is a
stronger claim: permitted evidence must change the distribution of future
proposals through run-scoped search state, persistent memory or libraries, a
proposal policy, or versioned model weights. Storing telemetry without changing
future decisions is observation; independent repeated samples are search, not
learner learning.

Every run records its learner-update level `L`. Persistent memory, learned
libraries, checkpoints, optimizer state, training data disclosures, and update
code are untrusted versioned artifacts with parents and rollback semantics. `L`
records the highest update class used; an explicit mechanism list prevents L3
weight updates from being misread as evidence that an L2 library was also used.

## 8. Generator interface

Candidate generators and learners are interchangeable and untrusted. Batch
generators may use the minimal interface:

```text
propose(
  parent_artifact,
  normalized_contract,
  permitted_search_evidence,
  generation_budget,
  feedback_summary
) -> candidate_manifest + candidate_artifact
```

Model-native learners instead use the episodic interface defined in Section 4.7
and the model-native design:

```text
open(parent, contract, action_schema, permitted_evidence) -> ProgramState
step(session, TypedProgramAction) -> ActionResult
probe(session, capability_scoped_request) -> ProbeResult
commit(session) -> candidate_manifest + candidate_artifact
```

`step` never executes candidate code with control-plane privileges. `probe`
accounts for every disclosed case, execution, token, and resource unit. A
rejected action remains in the construction trace so invalid attempts and repair
cost are not erased.

The same supervisor should support:

- enumeration or selection from known strategies;
- numerical parameter optimization;
- grammar-constrained or typed rewrites;
- complete typed IR generation and incremental semantic actions;
- equality-saturation extraction;
- genetic improvement;
- LLM-proposed source, complete IR, or typed action sequences.

Generator-specific behavior must not leak into promotion semantics. This is
essential for RQ6 and prevents an LLM demo from becoming the architecture. The
representation (`R`), generator (`G`), and learner update (`L`) are independent
treatments: for example, the same LLM can emit an unconstrained textual projection
of the kernel or typed actions, and a symbolic searcher can use the same action
protocol.

## 9. Evaluation design

Evaluation is layered from cheapest to most expensive:

1. manifest, mutation-scope, dependency, and capability validation;
2. parsing, type checking, linting, and static analysis;
3. deterministic unit, property, metamorphic, and differential tests;
4. adversarial and generated edge cases;
5. resource-constrained replay and microbenchmarks;
6. operational-holdout evaluation under the epoch-wide risk budget;
7. counterfactual twin-state shadow execution;
8. shielded staged canary execution;
9. post-promotion probation over the declared horizon.

Early success never skips a later mandatory gate. Gate order may be optimized for
cost only if logical requirements are preserved.

The post-freeze research audit is deliberately outside this operational
pipeline. It is run after current-study decisions are frozen to estimate
generalization, not to make a candidate eligible. Using the result operationally
retires the audit set for future confirmatory claims.

### 9.1 Correctness hierarchy

Preferred evidence, strongest first where applicable:

1. mechanized proof against a specified semantics;
2. exhaustive checking over a finite domain;
3. translation validation or equivalence checking;
4. differential testing against a trusted reference;
5. property and metamorphic testing;
6. example-based tests;
7. learned or human judgment.

The system records the evidence class. It must not describe test success as proof.

### 9.2 Measurement discipline

Performance evaluation must control or record warm-up, caching, CPU affinity,
frequency scaling, co-tenancy, input order, compiler flags, hardware, and repeated
trials. Noisy metrics use paired designs when possible and report uncertainty,
not only point estimates.

## 10. Promotion and rollback

### 10.1 Deployment leases

A candidate runs under an expiring lease specifying version, epoch, traffic
fraction, capabilities, start/end time, and rollback triggers. The application
cannot extend its own lease.

### 10.2 Independent observation

Health and correctness signals used for promotion or rollback must be collected
or attested outside candidate authority. Candidate-provided diagnostic telemetry
may supplement but never replace independent signals.

### 10.3 Champion/challenger policy

At most one champion owns the default traffic route. Multiple challengers may run
in isolated replay or shadow modes. Canary comparisons should use concurrent or
carefully paired traffic to reduce confounding by workload changes.

### 10.4 Counterfactual shadow and output shield

For the cache study, shadow is a counterfactual twin cache: it receives the same
request sequence but maintains its own cache contents and simulator-owned
recency/frequency snapshot. Candidate eviction choices evolve the twin’s future
state, so miss ratio is measurable, while those choices do not affect the served
cache.

During canary, an external output shield verifies that every selected victim is
currently evictable and unpinned. An invalid choice is counted as a candidate
violation, the reviewed fallback supplies the actual choice, and the candidate is
removed according to policy. Recovery is therefore defense in depth rather than
the only protection against this particular invalid effect.

### 10.5 State migration

The first prototype forbids candidate-private persistent state. All cache policy
features are supplied in the immutable per-decision snapshot and maintained by
the trusted simulator/reference monitor. Later stateful candidates must use an
explicit interface such as `(snapshot, state) -> (decision, new_state)` and
provide versioned snapshots, forward migration, backward recovery, invariant
checks, and fault tests. A candidate is not recovery-safe merely because its
executable can be replaced.

## 11. Lineage and memory

The candidate graph is not just version control; it is the system’s experimental
memory. It retains the immutable artifact/provenance identity and outcome of
failed and dominated branches to avoid rediscovering known failures and to
support diversity-preserving search. This does not require indefinite retention
of sensitive raw inputs: payloads follow their retention policy while hashes,
aggregate evidence, and deletion tombstones preserve the audit trail.

For every branch, record:

- what was changed and why;
- which evidence was visible during generation;
- which checks failed;
- objective vectors with uncertainty;
- environment and cost;
- whether the result later regressed under drift.

Summaries supplied to a generator must be derived views over this ledger and
carry their own version and hash.

## 12. Prototype architecture

The first implementation should favor inspectability over distributed-system
complexity:

- one host language with strong type and process-isolation support;
- a textual contract compiled to a canonical internal representation;
- a canonical typed candidate IR with an incremental action/observation API and
  deterministic human-readable projection;
- content-addressed local artifacts;
- an append-only embedded database for the ledger;
- isolated subprocess or container jobs with no network by default;
- a deterministic record/replay evaluator;
- a command that regenerates an entire candidate decision from its manifest;
- predefined and parameter-search generators before any LLM integration.

Implementation-language selection remains open. It should follow the minimal
semantic and isolation requirements rather than personal language preference.

## 13. Explicitly rejected shortcuts

- Giving the current champion write access to its installed artifact.
- Letting generated tests replace human- or specification-owned requirements.
- Keeping only the best score and discarding failed trials.
- Reusing a public benchmark indefinitely without tracking disclosures.
- Treating a container as a complete security boundary.
- Combining correctness and speed into one reward.
- Automatically adding dependencies proposed by a candidate.
- Promoting source different from the evaluated content hash.
- Reporting search cost only for successful candidates.
- Calling a statistically noisy win an improvement without a practical threshold.

## 14. Open design questions

The following require explicit decisions before implementation:

1. What is the minimal contract core, and which features belong in libraries?
2. What is the smallest candidate semantic kernel that separates benefits of
   typed actions from benefits of a domain-specific search space?
3. Which typed-hole and partial-program semantics keep intermediate states useful
   without making the kernel too restrictive?
4. Which host language best supports typed AST mutation and isolation?
5. Is the first artifact interpreted, compiled, or translated into policy code?
6. How are temporal data partitions enforced against repeated adaptive access?
7. What equivalence technique is feasible for the first target language?
8. What default dominance rule handles noisy multi-objective measurements?
9. How are model/API nondeterminism and unavailable proprietary models archived?
10. Which ledger representation supports both research analysis and operational
   replay?
11. What is the precise threat model of the chosen sandbox on the chosen platform?
12. When may an evaluator change, and what bridging evaluation preserves
    comparability across epochs?
13. When does a learned abstraction become shared vocabulary, and which
    equivalence, compatibility, and retirement evidence does that require?
14. Which learner updates may persist across runs or epochs without leaking
    protected evidence or invalidating comparisons?
